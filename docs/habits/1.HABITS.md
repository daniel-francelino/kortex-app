# Módulo Hábitos

O módulo **Hábitos** é o sistema de construção de hábitos do Kortex, inspirado explicitamente em *Atomic Habits* (James Clear): hábitos com "4 leis" (tornar óbvio/atraente/fácil/satisfatório), identidades ("eu sou uma pessoa disciplinada"), empilhamento de hábitos ("depois de X, farei Y"), streaks, revisão semanal e um heatmap de consistência. É o módulo mais extenso do Kortex hoje — mais de 30 endpoints, ~20 componentes e 13 migrations — e tem um módulo irmão fortemente acoplado, **Metas** (`/app/goals`), documentado aqui na seção 17.

Rota principal: `/app/habits` (`app/pages/app/habits/index.vue`, `layout: 'app'`). Rota secundária: `/app/habits/identity` (`app/pages/app/habits/identity.vue`).

> Como em [`1.NOTES.md`](../notes/1.NOTES.md) e [`1.JOURNAL.md`](../journal/1.JOURNAL.md), este documento descreve o estado **atual** do código, sinalizando explicitamente trechos que existem mas não estão acessíveis pela interface, e bugs/inconsistências encontrados durante a leitura do código (não suposições — cada um foi confirmado lendo o arquivo relevante). A lista consolidada está na seção 19.

## 1. Visão geral da tela

`/app/habits` é uma página única com **4 abas** controladas por um `ref` local (`activeTab`) — **sem sincronização com a URL** (trocar de aba não muda a query string, então não é possível linkar direto para "Insights", por exemplo):

- **Hoje** (`today`) → `HabitsTodayList`
- **Todos** (`all`) → filtros (busca/frequência/dificuldade) + `HabitsAllList`
- **Revisão** (`review`) → seletor de semana + `HabitsWeeklyReview` (+ botão "Configurações")
- **Insights** (`insights`) → `HabitsInsightsPanel`

Cada aba carrega seus dados **uma única vez**, de forma preguiçosa, ao ser visitada pela primeira vez (`watch(activeTab, ..., {immediate:true})` checando `status === 'idle'`).

A página monta, de forma controlada por `ref`s no nível da página: `HabitsDetailSlideover`, `HabitsCreateModal`, `HabitsShareImageModal`, `HabitsEditModal`, `HabitsArchiveModal`, `HabitsStackCreateModal`, `HabitsSettingsModal`.

### Tour guiado

Há integração pesada com `driver.js` (`useGuidedTour`): um tour geral (`HabitsOverview`) percorrendo as 4 abas, e um tour de "primeiro hábito" (`HabitsFirstHabitEntry` → continua dentro do `CreateModal.vue` como `HabitsFirstHabitCreate`) que inicia automaticamente quando o usuário tem zero hábitos — priorizado quando o usuário chega vindo do onboarding (`useOnboarding().pendingHabitHandoff`, setado no último passo do fluxo de onboarding, que já navega direto para `/app/habits`).

`/app/habits/identity` é uma página própria (não modal) para CRUD de identidades — grid de cards + modal de criar/editar com Zod (`{name, description}`). Acessível pelo botão "Identidades" no cabeçalho de `/app/habits` (só desktop) e tem botão "Voltar".

## 2. Aba "Hoje" (`HabitsTodayList.vue`)

Navegação de data (dia anterior/seguinte + badge "Hoje"), barra de progresso, card de celebração quando tudo está feito. Os hábitos são renderizados como **árvore somente-leitura** (`@he-tree/vue`, `<BaseTree>`), construída a partir de `habits` + `stacks`: pares de empilhamento definem pai/filho, e as raízes são os hábitos sem nenhum vínculo de entrada. Virtualização acima de 12 itens.

Cada linha (`HabitsTodayTreeRow.vue`) mostra: emoji-avatar ou ícone do tipo, nome (riscado se feito), badge de streak, badge de horário agendado, badge de dificuldade, badge de status de log, badge de "streak congelada", e **tooltips das 4 leis** ao passar o mouse (só para as leis que têm texto preenchido). No mobile, tocar a linha já alterna a conclusão; no desktop, tocar abre o slideover de detalhe e há um checkbox explícito.

Um modal de nota (por hábito) permite registrar uma observação junto do status escolhido (`done`/`done_later`/`skipped`).

> Para uma data que não é hoje, os hábitos exibidos vêm de `resolveHabitsForDate()` (baseado em `habit_versions`, ver seção 10), reconstruindo como o hábito estava configurado **naquele dia** — não como está configurado agora.

## 3. Aba "Todos" (`HabitsAllList.vue`)

Mesma estrutura de árvore, mas via `<Draggable>` do `@he-tree/vue` — arrastar-e-soltar reordena e re-empilha. Ao soltar (`@after-drop`), a árvore inteira é serializada e enviada para `PUT /api/habits/tree`, que persiste `sort_order` + recria os vínculos de `habit_stacks` de uma vez.

Cada linha (`HabitsAllTreeRow.vue`) tem alça de arraste, expandir/colapsar, menu (Editar / Empilhar-ou-Remover empilhados / Compartilhar / Arquivar) e os mesmos badges da aba Hoje.

Filtros: busca (texto), frequência, dificuldade — todos aplicados no servidor. Paginação via `UPagination`.

> ⚠️ **Bug de paginação confirmado**: `GET /api/habits` calcula `total` como o número de hábitos **raiz** da árvore de empilhamento, mas a página retorna galhos inteiros (um hábito raiz + todos os hábitos empilhados abaixo dele) — então uma página pode ter mais ou menos itens do que `pageSize`. É exatamente o bug já apontado no TODO interno da equipe (seção 1).

## 4. Aba "Revisão" (`HabitsWeeklyReview.vue`)

Navegação semana anterior/seguinte. Mostra a reflexão já existente da semana (somente leitura, com botão "Editar") ou um formulário de criar/editar (`wins`/`improvements`, texto simples, limite de 2000 caracteres) quando editável e ainda não existe reflexão. **Só a semana atual é editável** — semanas passadas são somente leitura na UI (a API em si não impõe essa restrição, é uma checagem só do cliente).

### Chave de semana — convenção própria, não é ISO 8601

`getCurrentWeekKey()` (em `useHabits.ts`) calcula uma chave tipo `YYYY-Www`, mas com **semanas começando no domingo** — diferente da semana ISO 8601 padrão (que começa na segunda). É uma convenção interna consistente entre `getCurrentWeekKey()`, `navigateReviewWeek()` e o próprio componente, mas o nome "semana ISO" não se aplica literalmente aqui — vale ter isso em mente ao ler o código ou o banco (`habit_reflections.week_key`).

O botão "Configurações" desta aba abre `HabitsSettingsModal.vue` (ver seção 12).

## 5. Aba "Insights" (`HabitsInsightsPanel.vue`)

Ao contrário do painel de insights do Diário (morto/desconectado), **este está totalmente ligado e funcional**. Mostra 6 cards de estatística (taxa 7d/30d, streak médio, melhor dia da semana, dias ativos, total de conclusões), um card de "destaques rápidos" (variação semanal da taxa, dia de pico, quantidade de hábitos ativos), cards de identidade "melhor"/"precisa de atenção", e embute `HabitsHeatmapChart` + `HabitsWeeklyRateChart` — cada um buscando `GET /api/habits/insights/heatmap?year=` de forma independente.

- **`HabitsHeatmapChart.vue`** — heatmap anual estilo GitHub, feito em SVG puro (sem biblioteca de gráficos), com tooltip via `Teleport`.
- **`HabitsWeeklyRateChart.vue`** — gráfico de barras (SVG/CSS) da tendência semanal de conclusão.

> ⚠️ **"Melhor dia" só considera os últimos 30 dias** (mesma janela usada para as taxas 7d/30d) — é "melhor dia dos últimos 30 dias", não um histórico completo, apesar do rótulo não deixar isso explícito.
>
> ⚠️ **O nível do heatmap (`level`, 0–4) é calculado como `conclusões do dia / total de hábitos ativos`**, não "conclusões / hábitos que estavam agendados para aquele dia" — em dias com poucos hábitos previstos, a intensidade de cor tende a aparecer mais baixa do que a consistência real sugeriria.

## 6. Criar e editar hábito (`CreateModal.vue` / `EditModal.vue`)

O maior componente do módulo (`CreateModal.vue`, 765 linhas). Formulário seccionado:
- **Campos base** (sempre visíveis): emoji-avatar (via `AppEmojiPicker` em popover), nome, descrição em rich text, seletor de dias da semana, dificuldade, tipo do hábito, tags.
- **Acordeão "Agendamento"** (carregado sob demanda): horário de início/fim (`UiTimePicker`), seleção de calendário.
- **Acordeão "4 leis"** (carregado sob demanda): seleção de identidade + os 4 campos de rich text (Tornar Óbvio / Atraente / Fácil / Satisfatório).

`CreateModal.vue` embute seu próprio tour `driver.js` (`HabitsFirstHabitCreate`), ativo só quando `guidedTourEnabled` (verdadeiro apenas quando o usuário tem zero hábitos).

`EditModal.vue` (567 linhas) segue a mesma estrutura, pré-preenchida via `watch(() => props.habit, ...)`, sem tour.

> ⚠️ **Bug confirmado**: `onClose()` do `CreateModal` não chama `resetForm()` — só um envio bem-sucedido reseta o formulário. Reabrir o modal depois de cancelar mostra dados de uma tentativa anterior. Já sinalizado no TODO interno da equipe.

## 7. Detalhe do hábito e calendário (`DetailSlideover.vue` + `Calendar.vue`)

`HabitsDetailSlideover.vue` (526 linhas) é uma visão somente-leitura: cabeçalho (emoji/ícone, nome, descrição em rich text, botões editar/compartilhar/arquivar), badges (tipo/frequência/dificuldade/identidade/janela agendada), cards de estatística de streak, card de identidade, tags, datas, as 4 leis (só as seções com conteúdo não-vazio aparecem), listas de empilhamento de entrada/saída (com botão de remover, desabilitado ao visualizar uma data histórica) e, no final, embute `HabitsCalendar`.

`HabitsCalendar.vue` (137 linhas) é um grid de mês (navegação anterior/seguinte) com tooltip mostrando nota/estado de conclusão por dia; dias futuros aparecem esmaecidos. Busca `GET /api/habits/[id]/calendar?year&month`.

> ⚠️ **O calendário por hábito não diferencia "dia não agendado" de "dia perdido"** — o endpoint preenche todo o mês com `completed:false` para dias sem log, sem considerar se aquele dia realmente era um dia previsto pela frequência/`customDays` do hábito. Um hábito semanal, por exemplo, mostra 6 de 7 dias como "não feito" mesmo que só um dia por semana fosse esperado.

## 8. Identidades

Modeladas como uma tabela própria (`identities`: `name`/`description` livres), ligadas 1:N a partir de `habits.identity_id`. Representam o conceito de "hábitos baseados em identidade" de *Atomic Habits* ("eu **sou** uma pessoa disciplinada", em vez de "eu **quero** ser disciplinado"). Alimentam o cálculo de "progresso por identidade" da aba Insights (`conclusões / conclusões esperadas` dos hábitos daquela identidade, em 30 dias).

Gerenciadas pela página `/app/habits/identity` (seção 1). O componente `HabitsIdentityManagerModal.vue`, que duplica quase toda a lógica dessa página como modal, **nunca é montado em lugar nenhum** — código morto, superado pela página dedicada.

> ⚠️ **Sem endpoint de restauração**: `DELETE /api/habits/identities/[id]` só arquiva (`archived_at`), e diferente de hábitos e metas (que têm `[id]/restore.post.ts`), **não existe nenhum jeito de reverter o arquivamento de uma identidade** pela API.

## 9. Empilhamento de hábitos (habit stacking)

Modelado como uma tabela auto-referenciada, `habit_stacks` (`trigger_habit_id → new_habit_id`): "Depois de [hábito gatilho], farei [novo hábito]". Um hábito pode ser gatilho de vários hábitos empilhados (ramificação), mas só pode estar empilhado **abaixo de um único** gatilho por vez (checado no servidor ao criar, e na validação de pai único ao sincronizar a árvore). Isso forma uma floresta de árvores, renderizada tanto na aba Hoje (somente leitura) quanto na aba Todos (editável por arrastar-e-soltar).

`server/utils/habit-stacks.ts` também torna os empilhamentos "sensíveis ao tempo": para uma data passada, retorna os empilhamentos que existiam até o fim daquele dia (`created_at <= fim do dia AND (archived_at IS NULL OR archived_at > fim do dia)`) — o mesmo espírito do versionamento de hábitos (seção 10), mas com uma janela simples de `archived_at`/`created_at` em vez de uma tabela de versões completa.

- **`HabitsStackCreateModal.vue`** — formulário de criar empilhamento (gatilho + hábito seguinte), montado pela página.
- **`HabitsStackingPanel.vue`** — código morto, nunca montado; superado pela edição via árvore de arrastar-e-soltar na aba Todos (confirmado pelo próprio TODO da equipe, que pede a remoção do botão "Empilhar" por esse motivo).

## 10. Versionamento de hábitos (`habit_versions`)

Um dos mecanismos mais sofisticados do módulo. `habit_versions` é um histórico **append-only** de cada configuração "significativa" de um hábito, chaveado por `(habit_id, valid_from)`, com `valid_to` fechando a versão superada.

- Uma nova versão só é criada quando a mudança toca um **campo versionado**: nome, identidade, descrição, as 4 leis, frequência/dificuldade/tipo, `customDays`, `sortOrder`, timezone, `calendarId`, horário de início/fim (`hasVersionedHabitChanges()`).
- **Uma versão por dia, no máximo** — uma constraint única (`UNIQUE(habit_id, valid_from)`) garante isso; múltiplas edições no mesmo dia colapsam na versão mais recente (upsert por `(habit_id, valid_from)`), em vez de fragmentar o histórico em sub-versões do mesmo dia.
- Todo `habit_logs` fica permanentemente vinculado a um `habit_version_id` — então a UI histórica (visões de "Hoje" para datas passadas, calendário por hábito, cards de compartilhamento) sempre reflete o hábito **como ele estava configurado naquele dia**, imune a renomeações/mudanças posteriores.
- `resolveHabitsForDate()` reconstrói "como os hábitos estavam" numa data arbitrária, juntando versões + `archived_at`/streak/identidade atuais, filtrando hábitos que já tinham sido arquivados antes daquela data.

## 11. Compartilhamento

Duas funcionalidades distintas, com maturidade bem diferente:

### Imagem de compartilhamento por hábito (funcional)

`HabitsShareImageModal.vue` busca `GET /api/habits/share/my-progress?habitId=`, renderiza um card fora da tela (`HabitsShareImageCard.vue` — gradiente, avatar/iniciais, estatísticas, frase motivacional) e usa `html-to-image` (`toPng()`, rasterização no cliente via canvas, não renderizado no servidor) para gerar um PNG 1080×1080, com opção de baixar ou usar `navigator.share()` nativo (com fallback para download).

### Link público de progresso (construído, mas inacessível)

Separadamente, existe `habit_user_settings.share_token`/`share_enabled` + o endpoint público (sem autenticação) `GET /api/habits/share?token=` — uma página de "meu progresso" pública. Duas falhas tornam esse recurso, na prática, morto:

- ⚠️ **Bug confirmado**: `server/api/habits/share.get.ts` nunca seleciona a coluna `id` de `habits` na consulta, mas o código depois faz `habits.map(h => h.id)` para montar a lista de IDs usada na consulta de taxa de conclusão. Como `id` nunca foi buscado, essa lista fica sempre vazia, e **`completionRate7d`/`completionRate30d` sempre retornam `0`** na página pública, não importa os dados reais.
- ⚠️ **Sem UI para ativar**: o único componente que expõe o toggle `shareEnabled` é `HabitsSettingsPanel.vue` — que **nunca é montado em lugar nenhum**. Ou seja, mesmo que o bug acima fosse corrigido, não existe hoje nenhuma forma de o usuário ativar o link público de progresso pela interface (ver seção 12).

## 12. Configurações (`SettingsModal.vue`)

O componente **realmente montado** (`HabitsSettingsModal.vue`, aberto pelo botão "Configurações" da aba Revisão) só expõe: dia da revisão semanal, toggle de lembrete + horário do lembrete. **Não tem nenhuma UI para `shareEnabled`/link de compartilhamento/geração de imagem.**

`HabitsSettingsPanel.vue` — código morto, nunca montado — é um superconjunto do modal acima: os mesmos controles de revisão/lembrete, **mais** um checkbox "Compartilhar progresso" (liga `shareEnabled`), uma URL pública copiável, e um botão "Gerar imagem para redes sociais" que abre `HabitsShareImageModal`. Por estar inalcançável, o recurso de link público (migration + endpoint + persistência de configuração, tudo pronto no backend) fica sem nenhuma porta de entrada na UI — a lacuna mais notável do módulo inteiro, no mesmo espírito do painel de insights morto do Diário, mas com impacto maior por deixar inacessível um recurso público inteiro.

## 13. Sincronização com o calendário (`habit-event-sync.ts`)

Sincronização **unidirecional** hábito → evento de calendário, acionada após todo create/update/restore de hábito com horário agendado:

- Constrói uma regra de recorrência (RRULE `FREQ=DAILY` ou `FREQ=WEEKLY;BYDAY=...`), calcula a primeira ocorrência no timezone do hábito (ou do usuário, `user_preferences.timezone`, padrão UTC) via `Intl.DateTimeFormat` manual — sem biblioteca externa de timezone.
- `getOrCreateHabitsCalendar()` cria, sob demanda, um calendário "Hábitos" (`#10b981`) na primeira vez que um hábito ganha horário e o usuário não tem nenhum calendário; caso contrário, usa o calendário explícito do hábito (se pertencer ao usuário) ou o primeiro calendário existente.
- Cada hábito com horário mantém **exatamente um** evento ativo — se o horário for removido, o evento é arquivado; se mudar, o evento existente é atualizado (com um snapshot em `event_history`).
- A duração do evento vem de `scheduled_end_time` (padrão de 30 minutos se não houver horário de término); a descrição é o texto puro (sem HTML) da descrição do hábito.

É uma projeção só de ida — **não existe sincronização de volta** (editar o evento no calendário não afeta o hábito) e **não existe "marcar como feito" a partir do calendário** — ambos aparecem como TODO explícito em `app/pages/app/appointments.vue` (bloco de comentário sem nenhuma implementação ainda).

## 14. Job de "pular automaticamente" (`cron-skip.post.ts`)

Endpoint de cron que marca como `skipped` todo hábito devido e não registrado numa data alvo (padrão: ontem) — evita que streaks/histórico tenham lacunas silenciosas. Protegido por um cabeçalho `x-cron-secret` comparado contra `runtimeConfig.cronSecret`.

> ⚠️ **Se `cronSecret` não estiver configurado, o endpoint fica sem autenticação alguma** — chamável publicamente.
>
> ⚠️ **Inconsistência confirmada com `today.get.ts`**: o filtro de "hábito aplicável" deste job trata hábitos `weekly` como devidos **todo dia**, enquanto `isDueOnDay()` (usado pela aba Hoje) trata hábitos `weekly` como devidos **só na segunda-feira**. Isso significa que o cron pode inserir logs `skipped` em dias que o hábito nunca esteve realmente previsto, poluindo `habit_logs` e o cálculo de streak. Vale notar que essa mesma função `isDueOnDay()` está **duplicada** (copiada, não compartilhada) em três arquivos diferentes do servidor (`today.get.ts`, `life/dashboard.get.ts`, `cron-skip.post.ts`) — o cron é a única cópia com a regra divergente.
>
> Itera sobre os hábitos de **todos os usuários** sem paginação/lote — possível gargalo de escala com muitos usuários.

| `habit_tags` | `id, user_id, name, color default 'gray', created_at, updated_at` | `UNIQUE(user_id, name)`. Tabela independente — sem taxonomia de tags compartilhada entre módulos. |
| `habit_tag_links` | `id, habit_id→habits(CASCADE), tag_id→habit_tags(CASCADE), created_at` | `UNIQUE(habit_id, tag_id)`. |
| `habit_user_settings` | `user_id PK, review_day, review_reminder_enabled, review_reminder_time, share_token UNIQUE, share_enabled, created_at, updated_at` | Configuração por usuário (não por hábito). `share_token` gerado uma vez, nunca regenerado. |
| `habit_cues` / `habit_rewards` / `habit_settings` | (schema original de gamificação: pistas/recompensas) | **Sem nenhum endpoint ou UI** — aparentam ser schema morto, superado pelas "4 leis". |

### Tabelas — Metas (Goals)

| Tabela | Colunas principais | Observações |
| --- | --- | --- |
| `goals` | `id, user_id, title, description, emoji, time_category, life_category, status, progress numeric, created_at, updated_at, archived_at` | `progress` recalculado só a partir de `goal_tasks` (trigger `recalculate_goal_progress`). |
| `goal_tasks` | `id, goal_id→goals(CASCADE), title, description, completed, sort_order, created_at, updated_at` | Toda mudança em `completed` dispara o trigger de progresso da meta. |
| `goal_habits` | `id, goal_id→goals(CASCADE), habit_id→habits(CASCADE), created_at` | `UNIQUE(goal_id, habit_id)` — **sem unicidade em `habit_id` sozinho**, então um hábito pode estar vinculado a várias metas ao mesmo tempo (contraria a intenção de produto documentada no TODO da equipe — seção 1). |

RLS habilitada em todas as tabelas (por `user_id = auth.uid()`, ou via `EXISTS` para tabelas filhas); como em Notas e Diário, os endpoints usam o client de service role e filtram `user_id` manualmente — RLS é camada extra, não o mecanismo de fato usado pela aplicação.

## 17. Relação com o módulo Metas (Goals)

- Uma **meta** pode ter vários **hábitos vinculados** (`goal_habits`), mas — ao contrário da intenção de produto documentada no TODO interno ("um hábito só pode estar vinculado a uma meta") — **nada no schema ou na API impede um hábito de estar vinculado a várias metas simultaneamente**.
- O **progresso da meta** vem exclusivamente da proporção de tarefas concluídas (`goal_tasks`, via trigger de banco `recalculate_goal_progress`) — **conclusões de hábito não influenciam o progresso em nada**, apesar da UI exibir hábitos vinculados e a barra de progresso lado a lado de um jeito que sugere relação. É um gap já documentado como desejado pela própria equipe.
- Excluir (arquivar) um hábito faz cascata (`ON DELETE CASCADE`) em `goal_habits`, removendo o vínculo silenciosamente — a lista de hábitos vinculados de uma meta simplesmente perde um item, sem nenhuma indicação de "este hábito foi excluído" (outro item do TODO interno).
- O vínculo é **unidirecional na UI**: só é possível vincular um hábito a uma meta a partir do slideover de detalhe da Meta (`GoalsHabitLinker.vue`) — não existe controle equivalente do lado de Hábitos (criar/editar hábito, slideover de detalhe do hábito) para "vincular a uma meta".
- **`GoalsCreateModal.vue`** não emite nenhum evento de criação, e `goals/index.vue` não escuta nenhum — resultado: **a lista de metas não atualiza depois de criar uma**, exigindo recarregar a página manualmente (bug confirmado, também já no TODO interno).
- **Aba de Insights não existe em Metas** — `GoalsInsightsPanel.vue` nunca é montado; a página de Metas é uma lista simples filtrável, sem abas.

## 18. Relação com o Life OS / Dashboard

Mesmo padrão já visto no módulo Diário: `GET /api/life/dashboard.get.ts` e `GET /api/life/insights.get.ts` consultam as tabelas `habits`/`habit_logs`/`habit_streaks`/`goals` **diretamente**, reimplementando (copiando, não compartilhando) a mesma lógica que já existe em `server/api/habits/today.get.ts`, `server/api/habits/insights.get.ts` e `server/utils/habit-versions.ts` — em especial, `isDueOnDay()` e o cálculo de taxa de conclusão 7d/30d estão duplicados byte a byte em vez de importados de um lugar só.

`DashboardTodayHabits.vue` e `DashboardInsights.vue` (em `/app/index`) são puramente apresentacionais — recebem os dados já prontos como props, sem nenhum conhecimento de `/api/habits/*`, e não permitem marcar um hábito como feito diretamente do dashboard.

## 19. Limitações e pontos conhecidos em aberto

1. **Componentes mortos** (nunca montados, confirmado via grep): `HabitsIdentityManagerModal.vue`, `HabitsSettingsPanel.vue` (o único com UI para o link público de compartilhamento), `HabitsStackingPanel.vue`, `GoalsInsightsPanel.vue`.
2. **Cadeia de endpoint morto**: `GET /api/goals/insights` → `useGoals().insights/refreshInsights` → nada chama.
3. **Bug no compartilhamento público**: `server/api/habits/share.get.ts` nunca seleciona `habits.id`, então as taxas de conclusão da página pública sempre mostram 0%.
4. **Recurso de compartilhamento público inalcançável**: ativar `shareEnabled` não tem UI viva (o único componente que expõe o toggle está morto).
5. **Bug de paginação** na aba "Todos": `total` conta hábitos-raiz, mas os dados retornados incluem galhos inteiros.
6. **Algoritmo de streak** assume cadência diária — incorreto para hábitos `weekly`/`custom`.
7. **Inconsistência `cron-skip.post.ts` vs. `today.get.ts`**: hábitos semanais são "sempre devidos" no job de cron, mas "devidos só na segunda" na visão Hoje ao vivo — o cron pode inserir logs `skipped` incorretos.
8. **`HabitLogStatus.DoneLater`** existe no banco/API mas não no enum TypeScript do frontend — status inalcançável pela UI.
9. **Sem UX otimista**: `logHabit()` refaz um fetch completo de `/api/habits/today` a cada marcação, em vez de atualizar o estado local otimisticamente (pedido explícito no TODO interno da equipe).
10. **Estado do modal não reseta ao cancelar**: `HabitsCreateModal.onClose()` não chama `resetForm()`.
11. **Lista de metas não atualiza após criar**: `GoalsCreateModal` não emite evento; `goals/index.vue` não tem handler.
12. **Cardinalidade meta↔hábito**: schema/API permitem muitos-para-muitos; intenção de produto (TODO) é um hábito por meta — não aplicado.
13. **Progresso da meta ignora hábitos**: só considera a proporção de tarefas concluídas, apesar da UI sugerir relação com hábitos vinculados.
14. **Sem restauração de identidade** (só arquivamento — diferente de hábitos/metas, que têm `/restore`).
15. **Exclusão de tag é definitiva** (hard delete) — inconsistente com o padrão de soft-delete usado no resto do módulo.
16. **`cron-skip.post.ts`** só é protegido se `runtimeConfig.cronSecret` estiver configurado; caso contrário, é um endpoint aberto e sem autenticação.
17. **Heatmap e calendário por hábito** não diferenciam "não previsto" de "não feito" — podem sub-representar visualmente a consistência real.
18. **`habit_settings`/`habit_cues`/`habit_rewards`** (schema original de pistas/recompensas) parecem não ter nenhum endpoint ou UI — provavelmente schema morto, superado pelo modelo das "4 leis".
19. **`fetchHistory()`** (histórico de mudanças do hábito) existe no composable, mas nenhum componente encontrado o chama — o histórico de mudanças parece não ter porta de entrada na UI.
20. **`isDueOnDay()` duplicada em 3 lugares** (`today.get.ts`, `life/dashboard.get.ts`, `cron-skip.post.ts`) em vez de compartilhada — risco de manutenção por si só, além da inconsistência já citada no item 7.
21. **Sem sincronização de volta do calendário**: editar o evento de calendário gerado por um hábito não afeta o hábito, e não é possível marcar um hábito como feito a partir do calendário (TODO explícito, não implementado).
22. **Sem taxonomia de tags compartilhada**: assim como Notas e Diário, as tags de Hábitos são uma tabela própria, sem relação com as de outros módulos.
23. **Trocar de aba não muda a URL** — não é possível linkar diretamente para "Insights" ou "Revisão", por exemplo (mesma limitação de "sem link direto" observada em Notas e Diário, mas aqui nem por abas dentro da própria tela).
